## 1. The bug does not reproduce on core through a real path

On `core-functionality` `70a0b84`, without this branch, I tried it on a real server:

1. A bot logged in to keep the chunk loaded.
2. The console ran `setblock 163 90 170 minecraft:chest` and `item replace block 163 90 170 container.0 with minecraft:diamond 4`.
3. The bot left, so the chunk unloaded.
4. I read the region file. The chest was saved with `Items: [{Slot: 0b, count: 4, id: "minecraft:diamond"}]`.

Core already serializes every live block entity into the chunk on all three save paths, through `World::save_block_entities`:

- chunk unload (`world/mod.rs` around 4994)
- `World::save`
- `World::shutdown`

The new test `chest_and_barrel_stacks_survive_dropping_the_live_entities` calls `world.block_entities.clear()` without saving first. No server path does that, so the test shows a problem the server cannot hit.

Please add a test, or a harness or console repro, that fails on current core through a real path: stop and start, chunk unload, or `/save-all` then a crash. If the real failure is in the chest window path, which I could not drive without a client, name that path.

## 2. If a real bug exists, fix it in the shared path

This branch serializes the whole container to NBT on every `set_stack` / `remove_stack` / `mark_dirty`, through `persist_container`. It adds a `bound_world: Weak<World>` to every chest and barrel to make that work.

That has two costs:

- It is per-type. Hoppers, droppers, dispensers, shulker boxes, furnaces and the rest would need the same treatment.
- It does full-inventory serialization on every slot change. Hoppers move items constantly.

The existing design is that the live entity is the source of truth while the chunk is loaded, and `save_block_entities` writes it on save or unload. If one save path skips that, add the call there once.

## 3. Smaller points

- `bind_world` is a new `BlockEntity` trait method that only these types implement. If the fix moves to the save path, it can go.
- The locking changes in `remove_stack` / `split_stack` are good on their own. They drop the item lock before `mark_dirty`. Keep them if you keep any per-change work.
