## 1. A periodic save can overwrite a newer logout save

`PlayerDataServer::tick` takes NBT snapshots on the tick thread, then writes them later on a `rayon::spawn` task. `handle_player_leave` writes directly. If a player logs out between the snapshot and the Rayon write, the order can be:

1. The leave save writes the newer data.
2. The Rayon task then writes the older periodic snapshot over it.

The per-player gate stops the two writes from overlapping, but it does not order them. The player loses whatever changed since the snapshot.

Fix: give each player a save counter.

- Bump it whenever a snapshot is taken.
- In `save_player_data_locked`, skip a write whose counter is older than the last one written for that UUID.
- Or simply skip periodic snapshots for players who have since left.

## 2. Smaller points

- `io_gates` keeps one `Arc<Mutex<()>>` per UUID forever. That is fine for normal servers, but it never shrinks. Removing the entry after a leave save would bound it.
- `handle_player_leave` runs inside the connection's async task (`lib.rs` around 621 for Java, 725 for Bedrock), so it runs on a Tokio worker. It now does gzip, `sync_all` and two renames there, which blocks the worker. `save_all_players` is called from the async `Server::save_all`. AGENTS.md asks not to block Tokio workers. Wrap the disk write in `spawn_blocking`, as the periodic path already uses Rayon.
